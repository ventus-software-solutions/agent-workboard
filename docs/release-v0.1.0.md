# Agent Workboard v0.1.0 Release Checklist

Use this checklist to cut the first Agent Workboard release. It assumes the release is a GitHub source release for the local-first app, not an npm package publish or hosted service launch.

## Release Scope

- Release version: `v0.1.0`
- Package version: `0.1.0` in `package.json`
- Release branch: create from current `main`
- Release artifact: GitHub release notes and source archive generated by GitHub
- Runtime target: local Docker Compose or local development on the operator machine

## Preflight

- [ ] Confirm `main` is the intended release head.
- [ ] Confirm the worktree is clean.
- [ ] Confirm `package.json` still has `"version": "0.1.0"`.
- [ ] Confirm `README.md`, `CONTRIBUTING.md`, `LICENSE`, `docs/architecture.md`, `docs/agent-spawning.md`, and `docs/roadmap.md` describe the current local-first boundary.
- [ ] Confirm `.workboard-data/`, uploads, screenshots, and other local operator data are not tracked.
- [ ] Confirm no pending release-blocking DOGFOOD tasks remain in `ready`, `in_progress`, `review`, `testing`, or `blocked`.

```bash
git checkout main
git pull --ff-only origin main
git status --short --branch
node -p "require('./package.json').version"
git status --ignored --short .workboard-data
```

## Verification Gate

Run these checks from a clean release candidate checkout.

```bash
npm ci
npm test
npm run build
npm run test:e2e
```

If Playwright cannot create `test-results/` in a restricted environment, rerun in a normal shell and record the reason in the release notes. Remove generated `test-results/` before tagging.

```bash
git status --short
git diff --check
```

## Docker Smoke

The supported one-command local run path is Docker Compose.

```bash
docker compose up -d --build agent-workboard
```

Smoke check:

```bash
docker compose ps
curl http://127.0.0.1:8088/api/health
```

Expected health response:

```json
{ "ok": true, "service": "agent-workboard" }
```

Stop the release smoke environment when finished:

```bash
docker compose down
```

## Changelog Draft

Use this as the initial GitHub release body and edit it for the final commit range.

```markdown
## Agent Workboard v0.1.0

First local-first release of Agent Workboard, a project and task board for coordinating AI agents through a browser UI, HTTP API, and MCP server.

### Highlights

- Multi-project kanban board with backlog, ready, in progress, review, testing, blocked, and done statuses.
- Task comments, activity history, attachments, completion records, and evidence-gated done flow.
- Live board refresh across browser sessions.
- Agent bootstrap docs, configured agent slots, presence, next-task selection, and stale-work handling.
- Agent Talks shared coordination channel for cross-task communication.
- Capability registry and operator approval queue for safer dogfood coordination.
- Local Docker Compose deployment pinned to `127.0.0.1:8088` by default.

### Verification

- `npm test`
- `npm run build`
- `npm run test:e2e`
- `docker compose up -d --build agent-workboard`
- `GET /api/health`

### Known Limitations

- Local-first and unauthenticated by default; do not expose directly to the internet.
- No hosted/team deployment model yet.
- No organization, RBAC, SSO, or audit-export system yet.
- Data is stored in local JSON files under `.workboard-data/`; operators are responsible for backups.
- GitHub push/tag/release steps require an authenticated local GitHub setup.
```

## Security Note

Agent Workboard v0.1.0 is a trusted local-operator tool. The default server and Docker Compose port publish are loopback-only for the host, and the app is unauthenticated. Do not deploy it on a public network or shared team host without a separate access-control boundary such as VPN, reverse proxy authentication, or another operator-approved control.

Before any hosted or team release, add authentication, project or organization isolation, permissions, audit posture, backups, and operational controls.

## Known Limitations To Include

- Local-first, single-operator trust boundary.
- Unauthenticated HTTP API and MCP surfaces.
- JSON file persistence in `.workboard-data/` instead of a managed database.
- Attachments are local filesystem files under the data directory.
- No automatic backup, retention, or migration export workflow.
- No hosted/team permissions, SSO, billing, or organization model.
- Release screenshots are manual; no generated media pipeline exists yet.

## Tag And GitHub Release Steps

Only tag after the verification gate, Docker smoke, screenshots, and release notes are ready.

```bash
git checkout main
git pull --ff-only origin main
git status --short --branch
git tag -a v0.1.0 -m "Agent Workboard v0.1.0"
git push origin v0.1.0
```

Create the GitHub release:

```bash
gh release create v0.1.0 \
  --title "Agent Workboard v0.1.0" \
  --notes-file release-notes-v0.1.0.md \
  --draft
```

Before publishing the draft release:

- [ ] Paste or upload the changelog draft after final editing.
- [ ] Attach screenshots if the repository release policy wants them on GitHub.
- [ ] Confirm the security note is visible in the release body.
- [ ] Confirm known limitations are visible in the release body.
- [ ] Confirm Docker run instructions point to `docker compose up -d --build agent-workboard`.
- [ ] Confirm no generated local data or screenshots were accidentally committed.
- [ ] Publish the GitHub release only after maintainer approval.

## Post-Release

- [ ] Announce the release with the local-first and unauthenticated boundary clearly stated.
- [ ] Create follow-up tasks for any release blockers that were deferred.
- [ ] Start the next PM grooming pass for post-v0.1.0 dogfood issues.
- [ ] If the release tag is wrong, do not rewrite it silently; create a corrective tag or release note after maintainer review.
